别让 Data Agent 猜数据是什么意思

OpenAI 展示了如何让 Agent 在 70,000 个数据集里做数据考古。更值得从头构建的，是一套让语义随数据一起产生、被验证和被执行的系统。

日期：2026-08-05

OpenAI 最近公开了它的内部 Data Agent。它运行在一个服务 3,500 多名内部用户、横跨 600 PB 数据和 70,000 个数据集的数据平台之上。为了回答一个看似简单的业务问题，它会综合表结构、历史查询、人工注释、生产代码、Slack、文档、长期记忆和运行时数据，再由模型判断该用哪张表、如何 join、应该加什么过滤条件。

这篇文章最容易让人得出的结论是：Data Agent 的关键是尽可能丰富的 context。

我的结论刚好相反。

如果一个 Agent 必须从代码、查询历史、内部文档和对话记忆中重新拼出一张表的含义，那么更根本的问题不是 context 还不够多，而是数据在产生时没有把自己的语义一起交付出来。

OpenAI 构建的是一套很强的数据考古系统。对于一个已经拥有数万数据集的大型组织，这可能是合理而务实的选择。但如果从头设计，系统的方向应该反过来：语义不应该在消费数据时由 Agent 事后推断，而应该在数据产生和转换的边界被声明、编译和验证。Agent 应该消费语义，而不应该成为语义的事实来源。

OpenAI 解决的是一个真实问题，但不一定是正确的目标架构

OpenAI 将自己的关键经验概括为：

“Schemas and query history describe a table’s shape and usage, but its true meaning lives in the code that produces it.”

这句话比“只看 schema 就能生成 SQL”前进了很多。代码确实包含 schema 看不到的过滤、粒度、更新方式和派生逻辑。但代码仍然不是语义本身。

代码记录的是实现，不一定是意图。它可能包含 bug，也经常只能解释系统做了什么，不能解释为什么这样做。历史查询告诉我们什么做法流行，却不能证明它正确。Slack 和文档可以记录业务背景，但它们可能已经过期。OpenAI 描述的 Agent memory 有用户确认和个人、全局两种 scope，但文章没有交代 global memory 的 owner、review、版本和回滚机制。

这些信息都很有价值，但它们的价值是作为证据，而不是自动成为权威定义。

OpenAI 的系统并非完全忽略权威来源。文章提到了人工维护的表注释、关键指标的 canonical definitions，以及用于评测的 golden SQL。真正的问题是这些权威定义仍然分散在文档、代码和人的记忆里，最后需要由 Agent 在运行时检索、解释和组合。至少从公开描述看，我们不知道这些来源冲突时采用什么 precedence，也不知道哪些定义经过了独立于 Agent 的版本化和执行约束。

这正是架构应该反转的地方。

数据产品的输出不应该只有数据

一个数据 pipeline 今天通常输出一张表或一组文件。更完整的数据产品应该同时输出：

  • 数据本身
  • 机器可读的语义
  • producer 与 consumer 之间的 contract
  • transformation 和 lineage
  • quality、freshness 与兼容性保证
  • access policy 和敏感性规则
  • 当前运行状态及其 provenance

这些信息不应该只是 catalog 里的一段说明，而应该与生产逻辑一起版本化，并尽可能进入 CI、构建和运行时检查。

这不是一个全新的方向。Zhamak Dehghani 在 Data Mesh 中已经主张把数据质量责任推到尽可能靠近源头的位置，让 data product 同时携带代码、数据、metadata 和 semantic declaration，并由平台自动执行 federated governance 制定的规则。Andrew Jones 在 2021 年的 Data Contracts 文章中也提出，数据应该像 API 一样被设计、记录和版本化，而不是把源数据库的内部结构直接暴露给下游，再让消费者自己推导含义。

关键变化是：semantics 本身也应该成为 pipeline 的正式产物。

例如，一个 orders 数据产品不能只输出若干列。它还需要声明一行代表订单、订单状态还是状态变更；金额是下单金额、支付金额还是确认收入；时间字段使用事件时间还是处理时间；取消、退款、测试账号和内部流量如何处理；哪些变化属于 breaking change。

当这些定义发生变化时，系统应该像检查 API 兼容性一样检查下游影响，而不是等到 Agent 的查询结果异常后再去阅读代码。

我想要的是一个 dbt-like semantic compiler

dbt 已经证明了一个重要模式：transformation 可以被声明为一个 DAG，和代码一起接受测试、构建、依赖分析和版本管理。dbt model contracts 还可以在构建前检查输出列名和类型是否符合约定；dbt Semantic Layer 则把 metric definitions 从 BI 工具移到 modeling layer，并统一处理指标和 join。

但现有 dbt 仍然不够。

Model contract 主要保证数据集的 shape，不保证 revenue 的业务含义正确；Semantic Layer 虽然提供 access permissions，但主要覆盖经过建模的指标，没有统一覆盖应用事件产生、流式系统、完整的隐私生命周期、运行时事故和端到端的数据生命周期。更重要的是，它通常从 warehouse transformation 开始，此时上游语义可能已经丢失。

真正需要的是一个更完整的 semantic compiler：

Producer contracts
        ↓
Transformation DAG
        ↓
Domain entities and metrics
        ↓
Quality, freshness and access policies
        ↓
Compiled datasets, lineage, tests and semantic query APIs

它的输入包括 source contract、transformation definition、entity、metric、dimension、policy 和 SLO；输出则包括可以执行的 transformation、兼容性检查、质量测试、lineage、权限判断、文档，以及供人和 Agent 共同使用的 semantic query interface。

在这个架构里，Agent 不再需要默认在 70,000 个数据集中自由探索。一次查询可以变成：

自然语言问题
  → 解析为 canonical entity、metric 和 dimension
  → 生成 semantic query plan
  → 检查权限和当前数据状态
  → 由 compiler 生成并执行 SQL
  → 返回结果、定义、版本和 provenance

LLM 负责理解人的意图和处理开放式问题。给定相同版本的语义定义、查询参数和 policy，semantic compiler 应该产生稳定、可审计的执行逻辑。模型可以选择指标，但不应该每次重新发明指标。

已经有人提出过相近方向

这个想法的组件并不新，甚至“Agent 应该建立在 semantic layer 上”也已经有人明确写过。

Cube 在 2025 年提出，semantic layer 的关键不只是 knowledge graph，而是一个能把高级请求确定性编译为 SQL 的 compiler。Agent 查询的是 approved、governed metrics，而不是自己处理底层 join 和 aggregation。

Snowflake Cortex Analyst 也明确承认，只给 LLM database schema 并不足以可靠生成 SQL，因为 schema 不包含业务流程和指标定义。它使用 Semantic Views 声明 logical tables、dimensions、facts、metrics 和 relationships，再把这些信息交给模型。

Databricks 对 semantic layer 的描述 更接近这里的论点：让 LLM 查询 governed metric definitions，而不是 raw tables；让定义进入 Git、review 和 CI/CD；让人、BI 工具和 Agent 使用同一个语义来源。

这些资料大多来自正在销售数据平台或 semantic-layer 产品的厂商，能证明这个方向已有明确的技术实践和多家厂商投入，不能单独证明它已经成为市场共识，或者在所有组织中都优于 OpenAI 的方案。

因此，这篇文章的主张不能是“我发明了 data contracts”或者“第一次发现 Agent 需要 semantic layer”。更准确的贡献是重新安排这些组件在系统中的权威关系：

信息类型 例子 在系统中的位置
声明的语义 contract、metric、entity、policy 经过 owner review 的权威定义
编译产物 SQL、schema、静态 lineage、测试 权威定义的可执行结果
运行时观测 实际 lineage、freshness、事故、质量结果 对“现在发生了什么”的带时间证据
推断信息 代码分析、query history、table similarity 发现缺口和检测漂移的辅助证据
Agent memory 用户纠正、局部约定、探索结论 有 scope 的候选知识，不能直接覆盖权威定义

OpenAI 的六层 context 解决了怎样选择和组合相关信息，文章也强调了减少工具重叠和加强验证。这里想继续追问一个公开描述没有回答的问题：当信息互相冲突时，谁有资格定义数据的含义？

这是 context engineering 和 semantic architecture 的区别。

“从源头获得”不等于让原始 producer 决定一切

把语义推向生产边界，也不能简化成“所有定义都由最上游应用团队负责”。

一种更合理的分工是：应用团队定义一个 event 为什么产生、字段是什么意思、哪些 invariant 必须成立；transformation owner 定义派生表的 grain、join、过滤和刷新方式；Finance、Product 或其他相关 domain owner 共同确认 recognized revenue、active user、retention 等跨数据源业务指标；跨域 identity、隐私分类和互操作规则则由 federated governance 协调。具体 owner 会随组织结构变化，但不应由 Agent 自己决定。

因此，“源头”不是唯一的一处原始数据库，而是每一种新语义被创造的地方。原始事实有自己的 producer，派生模型有自己的 producer，业务指标也有自己的 producer。每一层都应该对自己新增的意义负责。

这也意味着系统不应该追求一个包办所有业务语言的全局 canonical model。Data Mesh 强调 bounded context 和 polysemy 是有原因的。同一个 customer 或 revenue 在不同领域可能有合法的不同含义。平台应该统一 identity、contract 形式、版本和执行规则，而不是强迫所有 domain 使用一个定义。

最大风险不是技术，而是把它做成 YAML 墓地

任何 contract-first 方案最终都会遇到一个现实问题：谁来维护这些定义？

如果答案是让工程师再写一份不会被执行的 YAML，那么几年之后我们仍然会回到 OpenAI 的做法，让 Codex 阅读真实代码来猜文档哪里过期。dbt 自己也提醒，过早给仍在快速变化的 model 增加 contract 会提高维护和回滚成本。

所以不是每张临时表、每个探索性指标都需要立刻进入正式 semantic layer。Contract 应优先覆盖稳定、被复用、影响重要决策的边界。一个声明要成为权威，至少应该满足下列条件之一：

  • 能编译成 transformation 或 query plan
  • 能在 CI 中验证兼容性
  • 能在运行时检查质量和 freshness
  • 能控制访问和政策执行
  • 有明确 owner、版本和 review 记录

不能被执行或验证的自然语言描述仍然有价值，但它应该被标为 asserted context，而不是 contract。

Data Agent 仍然重要，只是角色应该改变

反转架构并不意味着 OpenAI 的六层 context 全部失去价值。

即使在理想系统里，运行时事故、临时实验、业务背景和新的探索性问题也不可能全部提前编译。声明的 lineage 说明应该发生什么，OpenLineage 这类运行时事件则提供一次执行中观测到的 metadata；它仍取决于 instrumentation 是否准确完整，但与设计时声明不能互相替代。Agent 仍然需要解释歧义、发现异常、组合外部知识，并在 contract 尚未覆盖的区域探索。

但 Agent 更适合承担四个角色：

  • 在遗留系统中做数据考古，生成 contract 候选
  • 比较声明、代码和运行时行为，检测 semantic drift
  • 遇到冲突时指出 provenance，并请求 owner 决策
  • 在没有正式语义的探索区工作，但明确降低答案置信度

一条从 query history 或代码中发现的规则，不应该悄悄写进 global memory 并成为新的事实来源。它应该变成一个可 review 的变更：由 owner 确认，进入 semantic definition，通过测试后发布。

这样，Agent 的学习闭环不再是“模型记住了更多东西”，而是“系统把一次发现转化成了可治理的知识”。

真正应该从头重建的是什么

对于已有 70,000 个数据集的组织，物理上推倒重来通常不现实。OpenAI 的数据考古方案可以帮助它逐步识别高价值表、补齐 contract，并把隐含语义迁移到正式的 control plane。

但如果讨论目标架构，我们确实应该从头重建一件东西：数据语义的控制面。

它不一定替换 warehouse、lakehouse、Spark、Airflow 或 dbt。它重新规定这些系统必须在边界上交付什么，以及 Agent 可以把什么当成真相。它让 declared semantics、compiled behavior、runtime observation 和 inferred evidence 各自拥有清楚的位置。

OpenAI 的文章更侧重展示如何让模型在既有数据世界里检索、验证和组合语义。下一步不应该只是继续改进这种能力，也应该让数据系统本身变得更容易理解、更难误用，更能解释自己。

模型不应该负责学会整个公司的数据架构。公司的数据架构应该主动把自己描述给模型，并且证明这份描述仍然是真的。

Stop Making Data Agents Guess What Data Means

OpenAI showed how an agent can perform data archaeology across 70,000 datasets. A better clean-sheet architecture would make semantics something the data system produces, validates, and executes.

Date: August 5, 2026

OpenAI recently published an inside look at its internal Data Agent. The agent operates on a data platform that serves more than 3,500 internal users and spans 600 petabytes of data across 70,000 datasets. To answer a seemingly simple business question, it combines schemas, historical queries, human annotations, production code, Slack, documents, long-term memory, and live system state. The model then decides which tables to use, how to join them, and which filters to apply.

The obvious lesson is that a Data Agent needs as much context as possible.

I came away with the opposite conclusion.

If an agent must reconstruct the meaning of a table from code, query history, internal documents, and conversational memory, the deeper problem is not a lack of context. The problem is that the data was produced without its semantics attached.

OpenAI has built a powerful data archaeology system. For a large organization with tens of thousands of existing datasets, that may be exactly the pragmatic solution it needs. But a clean-sheet architecture should reverse the direction: semantics should not be inferred after the fact when data is consumed. They should be declared, compiled, and validated at the boundaries where data is produced and transformed. The agent should consume semantics, not become their source of truth.

OpenAI Solves a Real Problem, but Not Necessarily the Right Target Architecture

OpenAI summarizes one of its most important lessons this way:

“Schemas and query history describe a table’s shape and usage, but its true meaning lives in the code that produces it.”

That is a major improvement over the idea that schema alone is enough for reliable text-to-SQL. Production code does contain filters, grain, refresh behavior, and derivation logic that schemas cannot express. But code still is not meaning itself.

Code records implementation, not necessarily intent. It can contain bugs, and it often explains what a system does without explaining why. Query history tells us what is popular, not what is correct. Slack and documents preserve business context, but they can become stale. OpenAI's Agent memory requires user confirmation and supports personal and global scopes, but the article does not explain ownership, review, versioning, or rollback for global memory.

All of these sources are valuable as evidence. That does not automatically make them authoritative definitions.

OpenAI does not ignore authoritative sources. Its article mentions domain-expert table annotations, canonical definitions for key metrics, and golden SQL used in evaluation. The issue is that these definitions remain distributed across documents, code, and institutional memory, leaving the agent to retrieve, interpret, and combine them at runtime. From the public description, we do not know the precedence rules when those sources conflict, or which definitions are versioned and enforced independently of the agent.

That is the part of the architecture I would reverse.

A Data Product Should Produce More Than Data

A data pipeline usually outputs a table or a collection of files. A complete data product should produce all of the following:

  • The data itself
  • Machine-readable semantics
  • A contract between producer and consumer
  • Transformations and lineage
  • Quality, freshness, and compatibility guarantees
  • Access policies and sensitivity rules
  • Current runtime state with provenance

This information should not live only as prose in a catalog. It should be versioned alongside production logic and, wherever possible, enforced through CI, build-time checks, and runtime monitoring.

This direction is not new. In her writing on Data Mesh, Zhamak Dehghani argues that accountability for data quality should move as close to the source as possible. A data product carries code, data, metadata, and semantic declarations, while the platform automatically enforces rules established through federated governance. Andrew Jones made a related argument in his 2021 essay on Data Contracts: data should be designed, documented, and versioned like an API, rather than exposing the internal structure of a source database and forcing every downstream consumer to reconstruct its meaning.

The important next step is to make semantics a first-class output of the pipeline.

An orders data product, for example, should not merely expose columns. It should declare whether one row represents an order, the current state of an order, or a state transition; whether an amount means order amount, payment amount, or recognized revenue; whether timestamps use event time or processing time; how cancellations, refunds, test accounts, and internal traffic are handled; and which changes are breaking changes.

When any of those definitions change, the system should analyze downstream impact the same way it checks API compatibility. It should not wait until an agent produces a suspicious result and then send the model back into the codebase.

What I Want Is a dbt-Like Semantic Compiler

dbt has already demonstrated an important pattern: transformations can form a declared DAG and participate in testing, builds, dependency analysis, and version control. dbt model contracts can check before a build that output column names and types match an agreed shape. The dbt Semantic Layer moves metric definitions out of individual BI tools and into the modeling layer, centralizing those definitions and automatically handling joins.

But existing dbt is not enough.

A model contract primarily guarantees shape. It does not prove that the business meaning of revenue is correct. The Semantic Layer supports access permissions, but its main scope is modeled metrics. It does not provide one unified system for application event production, streaming data, the full privacy lifecycle, runtime incidents, and end-to-end data lifecycle management. It also usually starts at the warehouse transformation layer, after important upstream meaning may already have been lost.

What we need is a broader semantic compiler:

Producer contracts
        ↓
Transformation DAG
        ↓
Domain entities and metrics
        ↓
Quality, freshness and access policies
        ↓
Compiled datasets, lineage, tests and semantic query APIs

Its inputs would include source contracts, transformation definitions, entities, metrics, dimensions, policies, and SLOs. Its outputs would include executable transformations, compatibility checks, quality tests, lineage, access decisions, documentation, and a semantic query interface shared by humans and agents.

In this architecture, the agent would no longer need to explore 70,000 datasets by default. A query could follow this path:

Natural-language question
  → Resolve canonical entities, metrics, and dimensions
  → Build a semantic query plan
  → Check permissions and current data state
  → Compile and execute SQL
  → Return results, definitions, versions, and provenance

The LLM would interpret human intent and handle open-ended questions. Given the same versioned semantic definitions, query parameters, and policies, the semantic compiler should produce stable, auditable execution logic. The model can select a metric, but it should not redefine that metric on every query.

Others Have Proposed Similar Directions

The components of this idea are not new. Even the narrower claim that agents should be built on semantic layers has already been made explicitly.

Cube argued in 2025 that what distinguishes a semantic layer from a generic knowledge graph is a compiler that can deterministically translate a high-level request into SQL. In this model, the agent queries approved, governed metrics rather than implementing joins and aggregations itself.

Snowflake Cortex Analyst similarly acknowledges that database schemas alone are insufficient for reliable text-to-SQL because they do not contain business process definitions or metric logic. Snowflake uses Semantic Views to define logical tables, dimensions, facts, metrics, and relationships before giving that information to the model.

Databricks' description of semantic-layer architecture comes even closer to this argument: let an LLM query governed metric definitions rather than raw tables; version definitions in Git and subject them to review and CI/CD checks; and give humans, BI tools, and agents the same semantic source.

Most of these materials come from vendors selling data-platform or semantic-layer products. They demonstrate concrete technical practice and investment by multiple vendors. They do not prove that the approach already represents market consensus or that it outperforms OpenAI's architecture in every organization.

The claim here, then, is not that data contracts are new or that no one has noticed agents need semantic layers. A more accurate characterization of the contribution is to rearrange the authority relationships between these components:

Information type Examples Role in the system
Declared semantics Contracts, metrics, entities, policies Owner-reviewed authoritative definitions
Compiled artifacts SQL, schemas, static lineage, tests Executable results of authoritative definitions
Runtime observations Observed lineage, freshness, incidents, quality results Time-bound evidence of what is happening now
Inferred information Code analysis, query history, table similarity Supporting evidence for finding gaps and detecting drift
Agent memory User corrections, local conventions, exploratory conclusions Scoped candidate knowledge that cannot directly override authoritative definitions

OpenAI's six layers of context address how to select and combine relevant information. The article also emphasizes reducing overlapping tools and strengthening validation. I want to push one step further and ask a question its public description does not answer: When those sources conflict, who has the authority to define what the data means?

That is the distinction between context engineering and semantic architecture.

“At the Source” Does Not Mean the Original Producer Decides Everything

Moving semantics toward production boundaries should not be simplified into giving the most upstream application team authority over every definition.

A more reasonable division of responsibility is for application teams to define why an event is emitted, what its fields mean, and which invariants must hold; for transformation owners to define the grain, joins, filters, and refresh behavior of derived models; for Finance, Product, or other relevant domain owners to agree on cross-source business metrics such as recognized revenue, active users, and retention; and for federated governance to coordinate cross-domain identity, privacy classification, and interoperability rules. The exact owners will vary by organization, but the agent should not choose them on its own.

The “source” is therefore not one original database. It is the boundary where each new piece of meaning is created. Raw facts have a producer. Derived models have a producer. Business metrics also have a producer. Each layer should own the meaning it introduces.

This also means the system should not force all business language into one global canonical model. Data Mesh emphasizes bounded contexts and polysemy for a reason. customer or revenue can have legitimately different meanings across domains. A platform should standardize identity, contract formats, versioning, and execution rules without forcing every domain to adopt one universal definition.

The Biggest Risk Is Building a YAML Graveyard

Every contract-first architecture eventually runs into the same practical question: who maintains the definitions?

If the answer is that engineers must write another YAML file that nothing executes, the organization will eventually return to OpenAI's approach and ask Codex to inspect real code to determine which documentation is stale. dbt itself warns that applying contracts too early to rapidly changing models can increase maintenance costs and make rollbacks harder.

Not every temporary table or exploratory metric needs to enter the formal semantic layer immediately. Contracts should focus first on stable, reused boundaries that affect important decisions. For a declaration to become authoritative, it should satisfy at least one of these conditions:

  • It compiles into a transformation or query plan
  • CI can validate its compatibility
  • Runtime systems can monitor its quality and freshness
  • It controls access or policy enforcement
  • It has a clear owner, version, and review history

Natural-language descriptions that cannot be executed or verified still have value. They should be labeled asserted context, not contracts.

The Data Agent Still Matters, but Its Role Should Change

Reversing the architecture does not make OpenAI's six context layers irrelevant.

Even an ideal system cannot precompile every incident, temporary experiment, piece of business context, or exploratory question. Declared lineage describes what should happen. Runtime events from systems such as OpenLineage provide metadata observed during a particular execution. Those observations still depend on accurate and complete instrumentation, but runtime observations and design-time declarations cannot replace each other. Agents will still need to interpret ambiguity, find anomalies, combine external knowledge, and explore areas not yet covered by contracts.

The agent is better suited to four roles:

  • Perform data archaeology in legacy systems and propose contract candidates
  • Compare declarations, code, and runtime behavior to detect semantic drift
  • Surface provenance when sources conflict and request a decision from the appropriate owner
  • Explore areas without formal semantics while explicitly lowering confidence

A rule discovered in query history or source code should not silently enter global memory and become a new source of truth. It should become a reviewable change: confirmed by an owner, added to the semantic definition, tested, and then published.

The learning loop then stops meaning “the model remembered more things.” It becomes “the system converted a discovery into governed knowledge.”

What Actually Needs Rebuilding

For an organization with 70,000 existing datasets, physically starting over is usually unrealistic. OpenAI's data archaeology system could help identify high-value datasets, fill contract gaps, and migrate implicit meaning into a formal control plane over time.

But if we are discussing the target architecture, there is one thing we should rebuild from first principles: the control plane for data semantics.

It does not have to replace the warehouse, lakehouse, Spark, Airflow, or dbt. It changes what those systems must deliver at their boundaries and what an agent is allowed to treat as authoritative. It gives declared semantics, compiled behavior, runtime observations, and inferred evidence distinct roles.

OpenAI's article focuses on helping a model retrieve, validate, and combine meaning in an existing data environment. The next step should not be only to improve that ability. We should also make the data system itself easier to understand, harder to misuse, and better able to explain itself.

The model should not be responsible for learning the company's entire data architecture. The data architecture should describe itself to the model, and prove that the description is still true.
